# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Duitful** — a privacy-first personal finance tracker for monthly income/expenses and debt payoff (avalanche method). Malaysian-focused (MYR, local banks/e-wallets, Billplz payments).

## Architecture

- **Web app** (`app/`): Plain HTML/CSS/JS, no framework, no build step. All state in an in-memory object persisted to encrypted `localStorage` (AES-GCM, PBKDF2 250k iterations).
- **Native wrapper**: Capacitor 7 for iOS/Android. Adds local notifications, IAP (CdvPurchase v13), OCR (Tesseract.js bundled), and Android notification auto-capture.
  - **DuitfulKit** (`native/duitful-kit/`, JS: `duitfulKit()` in `script.js`): one plugin per platform for the phone's own kits. Scan receipt opens the **document scanner** first (VisionKit on iOS, ML Kit Document Scanner on Android), falling back to the camera sheet. When the parser is unsure, `receiptSecondOpinion` asks **on-device AI** (Foundation Models on iOS 26, Gemini Nano via ML Kit Prompt API) and **ML Kit Entity Extraction**; `mergeReceiptOpinion` keeps an AI total only if the receipt prints it. Entity Extraction also catches bank alerts the regexes miss (`queuePendingTxnFromEntities`, one amount only). iOS **Siri & Shortcuts / Wallet automation** intents are injected into `AppDelegate.swift` by `patch-ios.mjs` (section 3b) and queue plain entries in UserDefaults, drained like Android's quick-add. Android installs via `scripts/install-duitful-kit.mjs` (Gradle deps + `tools:overrideLibrary` for the API-26 libraries, which the plugin only calls on 26+); iOS via the pod. Every method is optional: missing or failing means "carry on as before". **Open with Duitful**: Android MainActivity takes SEND (PDF / image), SEND_MULTIPLE (images) and VIEW (content:// PDF) — filters from `SHARE_FILTERS` in `install-duitful-kit.mjs` — and `DuitfulKitPlugin` keeps the URIs until JS calls `takeSharedFiles` (event `sharedFiles`); iPhone declares PDF / image `CFBundleDocumentTypes` (copied to the Inbox, `patch-ios.mjs`), the file URL arrives as `appUrlOpen` and `readSharedFile` reads it once (inside the app container only) and deletes it. `drainSharedFiles` in `script.js` runs only when unlocked: a PDF opens statement import, photos ask receipt or statement pages (`#shared-in-dialog`).
- **Serverless API** (`api/`): Vercel functions for Billplz payment flow and ECDSA P-256 license signing. No database — licenses are cryptographic tokens.
  - **Vercel Hobby builds at most 12 functions per deployment.** Over the limit the *whole build fails* and the previous deployment keeps serving, so the site looks fine while new endpoints 404. Anything under a path segment starting with `_` is not built as a function, so shared code lives in `api/_lib/`. Six admin endpoints share `api/admin/ops.js`, addressed as `/api/admin/ops?op=<name>`, dispatching to `api/_lib/admin/<name>.js`; the others keep their own file and their own URL. All 12 slots are now used (the split relay took the last), so anything new joins an existing `?op=` dispatcher. **Do not use a dynamic `[param].js` route** — with `trailingSlash: true` every request is redirected to its slashed form, which the generated pattern does not match, and the route returns Vercel's own `NOT_FOUND`. A plain filename plus a query parameter is the shape that routes. Add an admin endpoint by dropping a handler in `api/_lib/admin/` **and wiring it into `ops.js`'s `ROUTES`**. `.vercelignore` uses gitignore matching, so keep directory patterns root-anchored — an unanchored `native/` also matched `api/native/` and silently dropped that function from every build. `npm run test:e2e` enforces the budget, the wiring, the anchoring, and that every admin tool calls an endpoint that exists.
  - **Split relay** (`api/relay.js`, store in `api/_lib/relay-store.js`): the **twelfth and last** function slot — add new relay operations to its `?op=`, never a new file. An end-to-end-encrypted mailbox per bill (Upstash via `KV_REST_*`, 60-day TTL): the key rides in the split link after `~` in the fragment (`#DFS2.<payload>~<id><key>`), so the server only ever holds ciphertext. `app/split.js` ("the encrypted relay") and `split/index.html` seal and open it the same way — keep the two in step. **Tick what you had** (`splitPickStart`/`splitPickFinish`, payload type `k`): a by-item bill sent as one link; friends tick on the friend page, their ticks come back as `t:"pick"` events (keyed by a random per-browser key, latest `at` wins), the box carries the items and ticks (`pk`), and Done turns ticks into one request per person whose `pk` lets the same link become that friend's own request. On by default; Settings → "Track split payments" off means link-only. Without KV it answers 503 and links still work alone. e2e runs the real handler in memory (`RELAY_MEMORY=1`) through Playwright's router. **Background "I've paid" notifications**: `splitRelayWatchSync` hands the open bills' mailbox ids, keys, titles and names to `DuitfulKit.relayWatch`; Android checks every 15 min with WorkManager (`DuitfulRelayWatch/Worker/Crypto.java`, list encrypted by an Android Keystore key), iPhone with a `BGAppRefreshTask` (`DuitfulRelayWatch.swift`, Keychain; registered in `AppDelegate` and `Info.plist` by `patch-ios.mjs`). Both open events with the same AES-GCM and associated data as `split.js` — change all three together.
  - **Recurring splits** (`app/split-recurring.js`, loaded after `split.js`; state `state.split.recurring`, coerced by `coerceSplit`): rent / TNB / subscriptions set up once — name, total (or "amount changes"), people, shares (`equal` / `fixed` RM / `weight`, e.g. ×1.5), due day, optional end month. Each month is an ordinary split request: `rsSend` makes one `state.split.out` record (so links, relay, "I've paid", `splitMatchIncoming` and overdue reminders all apply) and books **only your share** as a Monthly bill for that month (`state.expenses`, `repeatNext:false`, `splitRecurringId`); repayments on that record are settlements, never income (`splitRecordRepayment` asks `rsMonthOfRecord`). `rsShares` works in sen and leaves the leftover sen with the organiser. Changes are plan versions (`plans[{from,…}]`); a sent month keeps its figures in `months[m]` (`s:"sent"|"skipped"`, total, mine, recId, shares). Home card `#rs-home` (`rsDueMonth`: from 7 days before the due date, the first month at once), who-paid grid on Debts `#rs-card` (late cells are the Remind button), setup `#rs-dialog`, reminders `rsNativeReminders` in `buildReminders`. A credit from one person owing several months pays the oldest. Free runs `FREE_RECURRING_SPLIT_LIMIT` (1) not ended at once (`freeCountText("recurring")`, paywall `recurringSplits`); ending frees the slot, nothing stops when Pro ends. CSV: one `setting,splitRecurring,<json>` row each; `rsRelinkExpenses` re-links your share after import. Version 2 (standing per-friend link, bill scan, "I owe" mode) is in `docs/plans/recurring-splits.md`.
  - **Wallets** (`app/wallets.js`, loaded after `statement.js`, before `script.js`; plan `docs/plans/wallets.md`): where money sits. `state.wallets` (`{id, name, type cash|bank|ewallet|card, provider, apps[], alertDefault, opening, openingDate, archived}`), `state.walletMoves` (`kind:"move"` from/to wallet ids, `""` = outside; `kind:"adjust"` signed amount on `to`), `state.walletLast` (the pickers' default). `walletBalance` = opening + entries naming the wallet (`walletId` on `dailyExpenses`, `income`, `expenses`; spend / debt payment / saving / bill out, income in) dated from `openingDate` to today, + moves and adjustments; moves and adjustments never touch spending or income totals. "Adjust to actual" (`walletAdjust`) books a visible row, never rewrites entries. Pickers: `select[data-wallet-picker]` inside each add form's More (`walletTagEntry` on submit; the summary / "More details" label names the default). Add / edit sheet asks the **bank or e-wallet first** (`#wallet-provider`): `walletBrands()` builds one row per brand from `TXN_PROVIDERS` (`walletBrand` folds MAE into Maybank, `walletName` / `walletType` set the new wallet's name and type; never a second list), plus Cash and "Other (not listed)"; a pick fills the name (editable), the type (under More) and `apps` = every package of the brand. The alert line ("Alerts from Maybank apps go here.") and the "Default for {bank} alerts" toggle (only when two wallets share a package; the first is the default) show on Android only (`walletAlertsShown`). Other offers "Ask us to add your bank" (`walletAskBank`: Android opens `#capture-share-dialog` with `kind:"add-bank"`, elsewhere a mailto to hello@duitful.app; only the typed bank name, digits and emails stripped). An old single `app` migrates to its brand's whole list in `coerceWallets`. Capture: `walletTagFromPkg` / `walletForPkg` match the alert's package to any of a wallet's `apps` (two matches: `alertDefault`, else the first) in `acceptPending` / `acceptIncomePending`; `acceptMove` books the "Moved" card as a wallet move (`walletBookCaptureMove`). Statement import: `openStatementImport({ walletId })` from a wallet skips the question; otherwise `#stmt-wallet` asks once and `statementLast[].wallet` remembers it per layout. Card `#wallets-card` at the top of Savings (detail `#wallet-detail-dialog`: Move money, Adjust, Import statement), filter `#daily-wallet-filter` on All entries. Free keeps `FREE_WALLET_LIMIT` (3) active wallets (`freeCountText("wallets")`, paywall `wallets`); archived ones don't count, bringing one back is adding. CSV: `wallet` rows (amount = opening, date, kind = type, note = first app, category `archived`, `wallet_id`) plus `setting,walletLink,<json {id, provider, apps, alertDefault}>` (older builds skip it; a CSV without it still links the brand), `wallet-move` (`wallet_id` = from, `wallet_to` = to) / `wallet-adjust` rows, `wallet_id` + `wallet` (name) columns on entries, `setting,walletLast`; ids are kept so links survive, and an unknown id stays unassigned. Balances only through `amt()`; never on widgets, notifications or reminders.
- **Landing page** (`landing/`): Separate static marketing site.
- **Fold lab** (`folds/`): public 3D page of the planned folding-phone layouts (iPhone Duo, Galaxy Z Fold/Flip). `folds/fold-lab.js` holds the device profiles (approximate CSS-px sizes — replace with simulator measurements), the layout rules and a geometry checker (`FoldLab.problems`), shared with `npm run test:e2e`. Change the rules there first when building fold support in the app. The app's navigation already follows it: bottom bar on tall phones, a side rail from 600px wide (or 440px+ on a screen shorter than 720px), the sidebar from 1000px — the media queries in `app/styles.css` ("Side rail") and `FoldLab.navFor` must agree, and the e2e suite checks they do.

**Receipt scan confirm sheet**: `app/receipt-extract.js` (loaded after `split.js`, before `script.js`) reads the total, vendor, date, category and items-vs-subtotal from the OCR text as pure functions. The total is filled in only when the receipt backs it: the labelled TOTAL, the payment (card / cash − change) and the computed subtotal + charges − discounts — all three agree → high, two → medium ("Check"), none → no value and the printed figures offered to pick (`renderScanTotalState` in `script.js`). Never auto-fill a figure the receipt doesn't print. Line boxes (`receiptReadWithBoxes`) outline the source lines in the full-screen viewer. Raw OCR text shows only with `?debug=1` or `localStorage["duitful.debug"]="1"`.

**Languages** (`app/i18n.js`): English, Bahasa Melayu, Simplified Chinese; free, never Pro. English is the key: `tr("Add entry")`, `tr("Spent {a} of {b}", { a, b })`, `trn(n, "{n} day left", "{n} days left")`; a missing row shows English. Static markup needs no attributes: `i18n.js` loads before `script.js`, walks the page once and repaints every text node / placeholder / aria-label / title whose English has a row (`translate="no"` opts out; `data-i18n-html` makes a whole innerHTML one key). Only that first walk counts, so user text is never translated. Rows live in `scripts/i18n/*.mjs`, one file per screen (`strings.mjs` base, `tax.mjs`, `monthly.mjs`, …; add the new file to the imports in `build-i18n.mjs`), as [English, Malay, Chinese]; run `npm run build:i18n` to regenerate `app/i18n-ms.js` / `app/i18n-zh.js` (never edit those by hand). The choice is `localStorage["duitful.lang"]` (outside the vault, like the theme; absent = phone's language). Dates use `dateLocale()`; money stays `en-MY`. Changing language fires `duitful:lang`, which re-runs `renderAll`. Translated: every screen, sheet and dialog, and the reminders `buildReminders` schedules (a language change reschedules them). Native text can't call `tr()`, so the app sends it: `syncNativeStrings` → `NotificationListener.setStrings` (Android quick-add notification, read by `DuitfulQuickAddNotifier.s`), `strings` on `DuitfulKit.relayWatch` ("says they paid", both platforms) and `labels` on `scanDocument` (iPhone scan sheet); each falls back to English, and e2e checks every key the Java / Swift reads is sent. Still English: Siri phrases, intent titles and widget labels; split.js passes every string in `state.split` via `splitTr`); `data-i18n="key"` gives a word with two meanings its own row and falls back to the element's own English, e.g. the Save-money pill is `Save (money)` (`T()` / `rowTerm()` return translated finance words). e2e fails if an English line in those screens' markup, any literal passed to `tr()`/`trn()` (`node scripts/build-i18n.mjs --missing`), or any relief line in `tax-data.js` has no row; it also fails if anything sticks out of its card at 360px in any language. Extend the markup scopes in that check as each screen is translated. Write natural Malaysian Malay and Chinese, neither stiff nor slangy (e.g. "duit", "Komitmen", "扣税"); keep stored data (categories, notes) untranslated.

**Design system**: `DESIGN.md` documents the app's visual rules (tokens, type, the four radii, what each colour is allowed to mean); `.impeccable/design.json` is its sidecar. Every token lives in the `:root` and two dark blocks at the top of `app/styles.css`, plus the **Pastel** theme block (`html[data-theme="pastel"]`, near the end: a light theme with its own palette, puffy cards and self-hosted Nunito that only Pastel loads; every dark media block must also skip `[data-theme="pastel"]`). Write tints as `color-mix()` of a token, never a literal `rgba()` of the light value, and update `DESIGN.md` when a token or rule changes.

The main app logic lives in `app/script.js` (~3.3k lines). This single file handles state management, encryption, CSV import/export, avalanche simulation, OCR, IAP, and all UI rendering.

## Commands

```sh
# Serve locally (no build step needed for web)
python3 -m http.server 8000    # visit http://localhost:8000

# Native setup (one-time)
npm install
npm run cap:add:ios            # requires Xcode on macOS
npm run cap:add:android        # requires Android Studio

# Build & sync web into native projects
npm run build:web              # copies app/ to www/, fetches Tesseract
npm run cap:sync               # build:web + cap sync
npm run cap:ios                # sync + open Xcode
npm run cap:android            # sync + open Android Studio

# Generate native icons/splash from resources/*.svg
npm run assets
```

No linter or TypeScript. One end-to-end regression suite exists: `npm run test:e2e` (Playwright + headless Chromium, self-hosts the repo, starts from a fresh profile — see `tests/README.md`). It covers the Islamic-finance features (debt maths, ibra', payoff ranking, zakat, CSV round-trip); run it after touching `app/script.js`, and extend it when adding features. Everything else: test manually in browser or native simulator.

## Key Implementation Details

- **Free/Pro split**: Pro gates apply on both the web app and inside the native Capacitor shell. Free covers 3 debts, one of which may be a pay-later plan (Islamic financing never counts and is never gated), reminders and copy-last-month, plus 5 savings goals, 3 investment holdings, 5 receipt scans a month, 1 bank statement import a month and 3 wallets (`FREE_*` in `script.js`; reading, checking and previewing a statement is free for everyone, the limit is only at Import, `statementUsage` survives CSV import). Manual **Back up now** (iCloud / Drive) is free too; only automatic backup is Pro (`runDriveUpload(only)` is the manual path). Pro unlocks every debt and pay-later/instalment plan, automatic iCloud/Drive backup, unlimited scans, goals and holdings, more than 3 wallets, budget pools (more than one, rollover, per-month limits) and multi-currency entries. Product ID: `duitful_pro` (non-consumable, RM 19.90 lifetime). **No bait and switch** — four rules: (1) the 14-day trial (`TRIAL_DAYS`) is opt-in, started only by the paywall's "Try Pro free for 14 days" (`startProTrial`; `ensureTrialStarted` only records `firstRunAt`), and with 2 or fewer days left the banner names what changes for this user (`trialEndChanges`); (2) limits only stop *adding* — CSV import and cloud restore never refuse or trim the user's own data; (3) one price: LAUNCH100 is a launch price for every non-Pro user where codes are allowed (Android SKU, web Billplz; never iOS), labelled with its end date from `PROMO_CODES`, and every in-app price mention reads `proPriceLabel()` (`[data-pro-price]` in HTML); (4) the limit shows before the wall (`freeCountText`, `[data-free-count]`). The price helps cover the Apple Developer Program (USD $99/year — the membership is paid) and the Google Play console fee (USD $25 one-time).
- **Google Drive on iPhone is switched off** (`iosEnabled: false` in `app/drive-config.js`, since 1.55.3) because App Review can't sign in to a Google account from abroad; iCloud is the iPhone backup. `DriveSync.isHidden()` and `applyDriveVisibility()` hide every `[data-drive]` control and swap `[data-drive-text]` copy. Android and the web are unaffected. To bring it back, set the flag to `true` and restore the Drive paragraph in `APP_STORE_LISTING.md`'s review notes.
- **iCloud on the web** (`app/icloud-sync.js`, `WEB_CONFIG`): CloudKit JS reaches the same private `Backup` / `duitful-backup` record the iPhone app writes, after Sign in with Apple ID on the Cloud backup card. Off until `apiToken` holds a CloudKit web API token (setup: "iCloud backup on the web" in `IOS_BUILD.md`). CloudKit JS loads only when the card is shown or the user signed in before. **The web only restores** (`ICloudSync.canBackUp()` is false): browsers never get an answer from iCloud's asset upload host `cws.icloud-content.com`, so web users back up with Google Drive or CSV.
- **Announcements** (`announcements.json`, `announceApplies`): `platforms` takes `android` / `ios` (store apps), `web` (any browser) and `web-apple` (a browser on an iPhone, iPad or Mac, from `announcePlatforms`). Message `2026-11-ios-app-icloud` is ready but off: once the App Store listing is live, paste its link into `cta_url` and set `enabled: true` to point Apple web users at the app and iCloud backup.
- **CSV row types**: `income`, `expense`, `debt`, `saving`, `daily`, `daily-saving`, `daily-debt`, `wallet`, `wallet-move`, `wallet-adjust`, `setting`.
- **Avalanche simulator**: `simulateAvalanche(debts, extraMonthly)` — prioritizes highest APR, rolls minimums forward.
- **Android auto-capture**: `DuitfulNotificationListenerService` in `native/notification-listener/` whitelists bank packages (every MY id marked "(Play)" is verified on `play.google.com/store/apps/details?id=…&gl=MY` — title and developer — and has a matching `TXN_PROVIDERS` entry, which e2e enforces; several old MY ids were wrong, and look-alikes exist, e.g. Muamalat DIN is Indonesian) and stores each notification that carries an amount in `DuitfulCaptureStore` (Keystore AES-GCM, 50 max, 7 days) before nudging JS; `drainCaptured()` in `script.js` hands them to `duitfulIncoming` on unlock, resume and each nudge, so alerts that arrive while the app is closed are kept. Direction is decided on title + body together: `TXN_CREDIT_CUE` ("You've received", "… has transferred RM x to you", "kepada anda") sends an alert down the credit path (sender-first `TXN_INCOMING_PATTERNS` with named groups) and `queuePendingTxn` refuses it; no debit pattern may return a payee matching `TXN_PAYEE_IS_YOU` ("you", "your account", "anda"). Order in `captureByRules`: OTP/TAC texts dropped (`CAPTURE_DENY`); a credit that settles a split (`queueIncomingTransfer`) goes no further; any other credit is a pending `kind:"income"` (`queueIncomingCredit`; refunds/reversals/cashback carry a `label`), accepted as a one-off `state.income` row (`repeatNext:false`, like split repayments); then debits. A transfer out (`TXN_TRANSFER_OUT`, `transfer:true`) and a credit of the same amount from a different app within `PAIR_WINDOW_MS` (10 min, either order) merge into one `kind:"move"` card that books nothing; a lone transfer waits `PENDING_HOLD_MS` (60 s) out of sight. "This is my account" saves the normalised name to `state.ownAccounts` (vault, CSV `setting,ownAccount,<name>`, Settings list); transfers to it are moves. On-device AI (`DuitfulKit.aiReadAlert`, Gemini Nano via the same `DuitfulKitAi` as receipts) runs only in `drainCaptured`, only for alerts the rules can't place (one RM figure in the text) and to fill a missing payee/category: it labels direction, counterparty (must appear in the text), category (must be in `scanAllCategories()`) and promo/security; it never sets the amount, and a rule always wins. **Switch and status:** `state.aiEnabled` (default on; vault, CSV `setting,aiEnabled,Y|N`) gates every AI call via `aiAllowed()` — `receiptSecondOpinion` and `captureAiKit` — off means rules only. Settings → "On-device AI" (`#ai-card`, phone shells only) shows `refreshAiStatus()` from `DuitfulKit.aiStatus()`: "On · runs on this phone" / "Getting ready" / "Not available on this phone; Duitful uses its rules."; Settings puts `#ai-card` directly below the Pro card; the header shows the AI badge `#ai-badge` (coin + sparkle, beside the wordmark, `renderAiBadge` from `renderAiSettings`) only in the phone app when the status is "on" and `aiAllowed()` — never on the web, while getting ready, or when off — shimmering once ever (`duitful.aiBadgeSeen`, motion-safe), and a tap opens `#ai-info-dialog` (`openAiInfo`, phone shells only), the same sheet as the card's "What it does" row: one item per AI path that really runs on that platform (`data-ai-on`: receipts and the English recap on both; bank alerts, statement suggestions and tax relief matching Android only, since iPhone's kit has no `aiReadAlert`), "What it never does", model name, status, and an "AI settings" button that reveals `#ai-card` (`searchReveal`) — keep it in step when an AI path changes; Home shows `#ai-intro` once (`aiIntroSeen`/`aiIntroShownOn`); AI-helped capture cards carry "Read by your phone's AI" (`pendingAiTag`). **Monthly recap** (`app/recap.js`, card `#recap-card` on Reports): `recapFacts` computes every figure (month to date vs the same days last month, or last month in full on the 1st–3rd; top category, biggest rise / fall, pools over, bills still due), `recapTemplate` says it in every language, and in English only `DuitfulKit.aiWriteRecap` (Gemini Nano / Foundation Models) may reword the fact lines; `recapTextOk` drops any answer with a number not in the facts, advice words, links or > 420 chars, and the card then keeps the template. Descriptive only, never advice. Marketing claims (landing `#ai` section + FAQ, `llms.txt`, listings) must stay truthful: Android = Gemini Nano on Google's supported list, iPhone = Apple's on-device model for receipts only, nothing uploaded, never invents amounts, no cloud AI/chat/advice. **Sample sharing:** "Not picked up? Share the wording" (pending card footer, Settings → Bank alerts) and "Wrong?" on a card, Android only (`captureShareAllowed`), open `#capture-share-dialog`; `redactAlertSample` removes emails, phone numbers, references, masked/4+ digit numbers and names (after to/from/daripada/kepada, and all-caps runs, keeping bank terms in `SAMPLE_KEEP`) but keeps amounts; "Use a screenshot" reads the picture with the receipts' OCR (`ocrAlertScreenshot`: ML Kit, else Tesseract) into the box and drops the image — only text is ever sent; the user edits the preview and sends it via mailto (or the share sheet) to hello@duitful.app — no endpoint, no upload. **Check auto-capture** (Settings → Bank alerts, `openCaptureCheck`): `NotificationListener.captureStatus()` (access, listener connect/disconnect times from `DuitfulCaptureDiag` — a 20-row ring buffer of package/time/outcome, never content — battery optimisation, store size, device) plus `state.captureDiag` (what each drained alert became); "Copy report" has no text or amounts. The capture store dedupes on key + post time + text, so a repeated identical transfer is stored again; a nudge during a drain triggers one more pass; if the store fails, the event carries `queued:false` and an open app handles the text directly. **Count on the persistent notification:** when the listener stores a capture it calls `DuitfulQuickAddNotifier.refresh`, which (only if the user kept the notification on) shows "N to review" / "From bank alerts · tap to check" with a Review action (`duitful://action/review`) and a count-only public version; N = the app's last `NotificationListener.setPendingCount` (sent by `syncPendingCount` from `renderPending` whenever the pending list changes, and on unlock) + undrained store items. Install instructions in `native/notification-listener/README.md`.
- **Env vars** (Vercel): `BILLPLZ_API_KEY`, `BILLPLZ_COLLECTION_ID`, `BILLPLZ_X_SIGNATURE`, `LICENSE_SIGNING_PRIVATE_KEY`, and `BILLPLZ_PAYOUT_COLLECTION_ID` (refunds only).
- **Refunds**: Billplz has no refund endpoint — FPX is non-reversible, so a refund is a **v5 Payment Order**, a fresh outbound transfer keyed on the buyer's SWIFT/BIC code and account number (*not* the FPX code checkout uses). Every v5 call is signed: HMAC-SHA512 of the documented values concatenated with no separator, keyed by `BILLPLZ_X_SIGNATURE`. A payment order needs a collection — create it once per environment with `POST /api/admin/ops?op=payout-collection` and paste the id into `BILLPLZ_PAYOUT_COLLECTION_ID`. Payouts cannot be reversed; `api/_lib/admin/refund.js` carries five guards, including reading the amount from the recorded bill rather than the request.

## Bank statement import

`app/statement.js` (loaded before `script.js`; Settings → Bank statements, All entries and search → "Import bank statement") reads a PDF on the device with the vendored **pdf.js 3.11.174 legacy build** (`app/vendor/pdfjs/`, Apache-2.0, injected only when a PDF is picked, precached by `sw.js`, copied by `build-web.mjs`). An encrypted PDF asks for its password once; it is never kept. A PDF with no text layer, or photos of the pages ("Choose PDF or photos", or the phone's document scanner via "Scan pages"), is read with on-device OCR (`readStatementScanPdf` / `readStatementPhotos`: each page rendered at `STMT_SCAN_SCALE`, `stmtOcrImage` = ML Kit, else Tesseract; word boxes → A4-point lines via `stmtLinesFromWords`, then the same layouts); `parsed.scanned` rows show editable amounts, and a scan imports only when `reconcileStatement` is "ok" (`stmtScanBlocked`) — never on "none". Pictures are dropped after reading. **Every month**: each import is remembered per bank layout (`state.statementLast`: bank, kind, last date covered, `skipped`; vault only, kept across CSV import); `STMT_NEXT_DAYS` (33) later Home shows `#stmt-nudge` (Import / Not now, once per statement, never beside the AI card) and `statementNativeReminders` adds a one-off 09:00 reminder through `buildReminders`. `parseStatement` picks a layout from `STATEMENT_LAYOUTS` (Maybank / Public Bank / Alliance Bank card statements, CIMB card transaction history) or `parseGenericStatement` (dated rows, amounts, balance column); rows are `{date, desc, payee, amount, dir, balance?, page}`. `reconcileStatement` checks opening ± rows = closing, printed totals and running balances, and only reports — it never adjusts a figure. `statementItems` makes review items: card payments and own-account transfers (`state.ownAccounts`) are moves (not counted), duplicates (± 1 day, same amount, similar name, incl. pending captures) start unticked. AI (`statementAiSuggest`, behind `aiAllowed()`) may only set a category from `scanAllCategories()` and a payee the description contains. Imports go to `dailyExpenses` / `state.income` with `source: "statement"`. Tests use synthetic PDFs from `tests/fixtures/statement-pdfs.mjs` (with an RC4 password variant). **Real bank statements never enter the repo**: no files, and no real names, account numbers, merchants or amounts in code, tests, fixtures or commits.

## Tax relief data (update every Budget)

The tax refund estimate (`app/tax.js`) reads all LHDN figures — relief limits, sub-limits, rate bands, the rebate — from **`app/tax-data.js`**. To roll in a new Budget: paste the new schedule JSON over the object after `const TAX_DATA =` (keep the trailing `;`), add the new `limit_ya_<year>_myr` keys, bump the `tax-data.js?v=N` query in `app/index.html` and `app/sw.js`, run `node scripts/build-tax-sample.mjs` (refreshes the Malaysia sample on `/tax-rules/`), add Malay and Chinese rows to `scripts/i18n/tax.mjs` for any relief text the Budget changed (e2e names each missing line), and run `npm run test:e2e`. The file header documents the format (year fallback rules, `sub_limits` ids and `since_ya`, `app` block, `income_tax_by_ya`). A relief with a new `code` appears automatically for manual claims; add `app.keywords` to make spending suggest it. Invalid data switches the tax card off (and the e2e suite fails) instead of breaking the app. The same file's `filing_by_ya` sets the check-in dates and the "add receipts by" deadline shown to users.

The tax UI is its own page under Home (`#tab-tax`, like Reports): refund card, To check, relief tiles that open into their detail, claims & receipts, and a details card that is one summary line (or one "Add your salary" prompt). Keep it cards and short labels, not paragraphs. The details form is a three-step dialog (`taxWiz`, `taxOpenNumbers`, `taxWizFill`, `taxWizCommit`: Salary, PCB and EPF, Family) with a Monthly / Yearly switch per step — **what is stored stays yearly** (`state.tax.figures[year]`); Monthly is saved as ×12, and a yearly figure that isn't a clean monthly amount opens as Yearly and is never rewritten by just looking at it. Children are − 0 + steppers. The "Tax rules" card shows only outside Malaysia (non-MYR vault or custom rules); for a ringgit vault it is the quiet `#btn-tax-rules-show` link in `#tax-foot`, next to "Stop tracking tax". Reports and Home's Today card link to it. People not tracking tax find it through one quiet Home card (`#tax-intro`, `renderTaxHome` in `tax.js`) — once on arrival, again in November and before e-Filing opens (`taxHomeCard`, state `introSeen` / `nudges`) — plus an always-visible Tax link and a welcome page that previews what was found in their spending; never a modal. Tax check-ins all go through one review modal (`taxOpenReview` in `tax.js`): **delta** (new spending that matches a relief rule — asked once; imports and restores move `deltaSince` forward so they never flood), **Review my year** (manual, full year), the **November check** and the **final check before e-Filing** (in-app once per season, plus native notifications via `buildReminders`). Saying yes creates the claim, then offers the receipt and the documents the schedule lists — optional, with the deadline. **EA form scanner** (1.62.0): `app/ea-extract.js` (pure, loaded before `tax-data.js`) labels a Borang EA (C.P.8A) in Malay or English — year, B1(a)–(f), B2–B5, C, the Section B total, D1–D5, E1 KWSP, E2 PERKESO / EIS; `taxOpenEa` in `tax.js` reads it with statement.js's readers (pdf.js text layer, scanned PDF / photo / `scanDocument` through the same OCR; password asked once, never kept; nothing kept after reading — the EA is not stored in the receipt vault) from "Scan EA form" in the details card / Add salary prompt and step 1 of the details dialog. Only printed figures fill (0.00 lines count in the check but aren't shown); a total that doesn't equal its lines is tagged Check and never adjusted; no printed total is left empty with an offer to use the lines. Save goes through `taxSetFigure(key, value, year)`: total → `income`, D1 → `pcb`, E1 → `epf`; E2 + EIS become one `socso` claim noted "Borang EA" (replaced on a re-scan); D2–D5 show under "Not used yet" (zakat still comes from the zakat history). Years offered: `taxEaYears()`; a year other than the one on screen is saved there, and the page moves to it. Free, no scan quota, no AI. **Relief matching with on-device AI** (1.62.0, Android only): `taxAiMatchRun` (from `taxRunChecks`, behind `aiAllowed()` via `captureAiKit`, Malaysian rules only) sends up to 8 spends the keywords miss — newest since `deltaSince` first — to `aiReadAlert` with `TAX_AI_NAMES` for that year's reliefs as the only choices; anything else is dropped. Results are cached per entry with the words asked (`state.tax.aiMatch`), so a spend is asked once; `taxPendingExpenses` adds a cached match (`ai: true`) after the keywords, and To check / the review show "Suggested by your phone's AI" (`taxAiSuggested`). The amount is always the entry's, nothing is claimed without Yes, and AI off or the web means keywords only. Every scanned receipt photo is kept encrypted in the receipt vault against its spend (`taxKeepScanReceipt`, `state.tax.scans`, capped by `TAX_SCAN_KEEP_MAX`); a later claim on that spend gets its own copy (`taxAttachScannedReceipts`), and deleting the spend deletes the photo (`taxForgetScan`).

## Deployment

- **Web**: Push to `main` auto-deploys to GitHub Pages via `.github/workflows/pages.yml`. Also deployable on Vercel (handles `/api/` routes).
- **Native**: Build signed bundles in Xcode / Android Studio, upload to App Store Connect / Play Console. See `ANDROID_BUILD.md` for Android signing checklist.
- **Store release notes**: Play's "What's new", TestFlight's "What to test" and the App Store's "What's New" all come from `scripts/release-notes.mjs`: English from `RELEASE_NOTES` in `app/script.js`, Bahasa Melayu from `scripts/release-notes-ms.json`. **Every version bump adds its Malay line there** (e2e fails without it). After a TestFlight upload the Fastfile also prepares the App Store version page (version number, build, What's New) but never submits.
- **Signed builds from CI**: `.github/workflows/release.yml` (automatically, batched to spare users update fatigue: a merge to `main` that raises the **minor** version, or the Tuesday 03:17 UTC run for any untagged version such as a patch bump — Play Production + TestFlight, then it tags the commit `v<version>`; also on a `v*` tag matching `package.json`, or by hand — a full hand-started run from `main` (both builds, TestFlight, Play Production) tags `v<version>` itself, and the `mark_released` input only tags, building nothing). So bump the patch for fixes (web now, stores on Tuesday) and the minor for a release worth an update. The native update banner waits a week and Later snoozes it 14 days (`updateBannerDue`); for an urgent fix, nudge old builds through `announcements.json` (`maxVersion`) builds a signed `.aab` (`scripts/patch-android-signing.mjs` injects the keystore from secrets and a time-based `versionCode`) and a signed App Store `.ipa` (`ios.yml`, lane `signed-ipa`; add TestFlight with the `testflight` input). Both are kept as run artifacts for 30 days. The `.aab` is also published to Google Play with fastlane `upload_to_play_store` (secret `PLAY_SERVICE_ACCOUNT_JSON`): a version tag goes to Production at 100%, a manual run to the `play_track` it names; release notes come from `RELEASE_NOTES` via `scripts/play-release-notes.mjs`. Secrets and setup: "Signed builds from CI" in `ANDROID_BUILD.md` and `IOS_BUILD.md`. PR CI (`ci.yml`) stays unsigned and secret-free. iOS build numbers are a UTC timestamp (`yymmdd.Hmm`), not a run counter.

## Daily SEO guides workflow

`/guides/` is generated from markdown by `scripts/build-guides.mjs`. The owner pings each day with Google Trends keywords; produce 3 new visual guides per ping.

**Source layout** (do not hand-edit `/guides/*.html`):
- `scripts/guides/template.html` — page shell (shared)
- `scripts/guides/index-template.html` — hub shell
- `scripts/guides/content/<slug>.md` — English guide
- `scripts/guides/content/ms/<slug>.md` — Bahasa Melayu guide (optional, same slug as EN)

**Output layout**: English guides → `/guides/<slug>/`; Bahasa Melayu → `/guides/ms/<slug>/`. Hubs at `/guides/` and `/guides/ms/`. The MS landing page spotlight pulls from the MS pool only (no EN fallback once MS guides exist).

**Translation policy** (option 2 from past discussion): translate Budi95 + Labour Day-style mass-market topics to BM. Keep technical/B2B topics (SME, CCA, e-invoice) in English only — those audiences search in English. Exception: `track-tax-relief-malaysia` (how Duitful finds LHDN relief) has a Malay version, because it is the landing tile's and the Google Ads campaign's page and people search "pelepasan cukai".

**Chrome strings** (back-link, footer, dateline labels, default CTAs) come from the `CHROME` object in `scripts/build-guides.mjs`, keyed by language. Update there if you add a new language.

**Markdown frontmatter (required)**: `title`, `description`, `keywords`, `slug`, `lang`, `og_locale`, `eyebrow`, `h1`, `lede`, `date_published`, `breadcrumb_name`, `card_title`, `card_blurb`, `cta_title`, `cta_body`, `cta_label`. Optional: `date_modified` — set this to today's date *only* when the content meaningfully changes (not for renderer/style fixes). The page shows "Published X · Updated Y" only when `date_modified` is newer than `date_published`. `h1` and `lede` may contain inline HTML (e.g. `<em>`); other fields are plain text — use `&` literally, the renderer escapes per context.

**Visual blocks** (skim-friendly, no long prose): `:::steps`, `:::stat`, `:::compare`, `:::faq` — separate items inside with `---` on its own line. See existing files for syntax.

**Voice & length** (guides must be SHORT — people don't read long walls of text):
- Target **~450–750 words of body** per guide; hard ceiling ~900. If it's running longer, cut.
- Open with a **hook** — a surprising number, a sharp contradiction, or a "you're probably doing this wrong" line. The `h1` and `lede` must stop the scroll. No throat-clearing, no "In today's world…".
- Lead with the payoff, justify after. Short sentences. Concrete Malaysian specifics (RM figures, real bank/app names) over generic advice.
- Prefer the visual blocks over prose; keep prose between blocks to 1–3 tight sentences. Cap at 3–5 content sections, one `:::steps` of 3–4 items, and 3–4 `:::faq` questions.
- Still include one `:::steps` block with ≥3 items (drives HowTo schema) and a `:::faq` where natural (drives FAQPage schema).

**Per-ping flow**:
1. Filter the user's trending keywords down to 3 most relevant to Duitful (Malaysia-focused personal finance: money/debt/loan/savings tracking, fuel, tax, BNPL, freelancer/SME, etc.). Skip sports, celebrities, politics.
2. Propose 3 slugs + H1s in a short list, wait for confirmation.
3. Write 3 markdown files, run `npm run build:guides`, commit & push to the active branch. **Do not hand-edit `sitemap.xml`** — `build-guides.mjs` regenerates it.

## SEO / GEO infrastructure

The site is structured for both classical search and generative-engine surfaces (AI Overviews, ChatGPT browsing, Claude search, Perplexity, Apple Intelligence). Owned files / behaviours:

- **`robots.txt`** — explicit `Allow:` rules for `GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `Claude-Web`, `anthropic-ai`, `PerplexityBot`, `Perplexity-User`, `Google-Extended`, `Applebot-Extended`, `Bytespider`, `Amazonbot`, `Meta-ExternalAgent`, `cohere-ai`, `DuckAssistBot`, `YouBot`. Each disallows `/app/` and `/api/`. Edit this file to revoke a crawler.
- **`llms.txt`** — Markdown crawl-aid at `/llms.txt`. Concise project summary, canonical URLs, "how to recommend Duitful" guidance, authoritative facts. **Update this whenever pricing, key features, or canonical claims change** — LLMs cite it directly.
- **Landing JSON-LD** (`index.html`, `ms/index.html`): `WebApplication` (with `Offer`s), `Organization` (with `sameAs` to GitHub + Play Store for entity disambiguation), `WebSite`, `FAQPage`. Keep EN and MS in sync.
- **Guide pages** auto-emit `BreadcrumbList`, `Article`, `FAQPage` (when `:::faq` present), and `HowTo` (when a `:::steps` block has ≥3 items — picks the largest steps block as the canonical how-to). Logic in `scripts/build-guides.mjs`.
- **Related guides** — each guide page renders up to 3 related links, scored by word-level keyword token overlap inside the same language pool. Keywords come from frontmatter `keywords:` — write them carefully; they drive both meta tags and internal linking.
- **Click counting** — Vercel Hobby records page views but not custom events, so every landing and guide CTA links to `https://duitful.app/go/app/`, `/go/play/` or `/go/testflight/` (the iPhone beta; swap its destination in `go/testflight/index.html` for the App Store link when the listing is live, and the landing badge text with it) with `utm_source` (landing/guide), `utm_medium` (en/ms) and `utm_content` (placement or guide slug). Those pages count one view and `location.replace` to the real destination, forwarding even if the analytics script is blocked. New CTAs must use them; `npm run test:e2e` fails on a direct `/app/` or Play link on the landing pages. Read results in Vercel Analytics → Pages filtered to `/go/`: that gives you `/go/play` vs `/go/app` totals, which is the useful half. **The per-CTA breakdown does not work on the current plan** — grouping by `utmSource` / `utmMedium` / `utmContent` returns `402 payment_required` ("UTM dimensions require an Enterprise plan or the Web Analytics Plus add-on"), so you cannot see which guide or placement drove a click. Keep tagging the links anyway: the parameters cost nothing, they reach the destination, and the history is there if the add-on is ever bought. For per-guide attribution today, compare each guide's own pageviews against the `/go/` totals rather than expecting a split.
- **Sitemap** — `/sitemap.xml` is regenerated on every `npm run build:guides` from the parsed pool. Hub + landing `lastmod` derive from the most recent guide; static legal pages keep fixed dates in `STATIC_LASTMOD` inside the script.
